The Intacct PM lens: turn a product question into evidence.

You already know the objects, processes, and customer outcomes. The harness helps connect that product understanding to the source-backed details behind an entity: code, data shape, APIs, actions, security, dependencies, and test evidence.

PM takeaway It shortens the path from “what should Intacct do?” to “what do we know, where is it implemented, and what still needs proof?”

What changes for a PM?

The product question stays in your language; the evidence becomes traceable.

01

Start with the business object

Use a canonical entity such as APBill or GLAccount as the anchor instead of beginning with a filename or a guessed service.

02

Follow the surfaces

Move from entity to implementation roots, schema, workflow/action, REST/OpenAPI, access, and code relationships.

03

Make uncertainty visible

Exact mappings and source paths are evidence. Missing, unresolved, or partial coverage stays visible for a deliberate follow-up.

What “evidence” means here

Different stores answer different questions.

Authoritative factsSQLite

Stores extracted facts, mappings, provenance, and validation evidence. Use it to ask: “What do we know?”

Source trailFiles + symbols

Keep the answer connected to a real source artifact, symbol, configuration entry, or authored test case.

ConnectionsLadybug graph

Supports traversal, dependency, and impact questions. It is a rebuildable projection and can lag SQLite.

Decision signalKnown / partial / unresolved

The result should tell you whether to decide, ask engineering, or request more validation.

Three useful PM boundaries

These are the moments where a confident-looking answer can mislead.

Do not overread

Coverage is not completeness

An endpoint, mapping, or authored case proves that evidence exists. It does not prove every customer path or integration is represented.

Ask for the next proof

Unknown is a valid result

If the source does not establish a relationship, treat it as a discovery task—not permission to fill the gap from naming intuition.

Keep the distinction

Discovery is not execution

The harness supports impact analysis and test planning. Runtime, integration, API, and end-to-end behavior still need their own validation.
